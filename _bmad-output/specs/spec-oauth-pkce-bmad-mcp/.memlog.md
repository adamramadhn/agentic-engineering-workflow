- (note) Fakta klien Go (internal/auth/oauth.go): memanggil grant_type=refresh_token ke /api/oauth/token (grant ini TIDAK terdefinisi di WEB_SPEC) — refresh grant wajib masuk scope; klien juga mem-parse error=access_denied+error_description di callback dan cek user.isAllowed di setiap respons.

- (decision) Slug spec: oauth-pkce-bmad-mcp.
- (decision) Access token MCP = JWT HS256 ditandatangani AUTH_SECRET, klaim audience bmad-mcp; verifikasi stateless tanpa lookup DB per request (pilihan user atas opaque token).
- (decision) Gerbang isAllowed dipetakan ke users.status='Active' — tanpa migrasi kolom baru (pilihan user).
- (decision) Refresh token MCP mirror pola web: JWT ber-jti, sha256(jti) di DB, rotasi tiap pemakaian, deteksi reuse, revoke saat user non-Active (pilihan user).
- (decision) Halaman /oauth/authorize reuse gaya auth-shell (src/components/auth/); tanpa sesi web redirect /login berikut next; tombol Authorize + Tolak; Tolak = redirect callback error=access_denied.
- (decision) Endpoint REST BMad (/api/projects/**, /api/llm-providers) diverifikasi dual-auth: cookie sesi web ATAU Authorization Bearer aud=bmad-mcp; token web dan MCP tidak saling diterima.
- (capability) CAP-1 Halaman persetujuan GET /oauth/authorize: user bersesi web dapat menyetujui/menolak permintaan otorisasi MCP; hasilnya redirect loopback callback berisi code+state atau error=access_denied.
- (capability) CAP-2 POST /api/oauth/token grant authorization_code: klien menukar code sekali-pakai dengan pasangan token + profil user; PKCE S256 wajib cocok.
- (capability) CAP-3 POST /api/oauth/token grant refresh_token: klien memperbarui sesi kedaluwarsa tanpa login ulang; rotasi, deteksi reuse, dan revoke saat non-Active.
- (capability) CAP-4 Proteksi Bearer di REST BMad: /api/projects/** dan /api/llm-providers hanya melayani cookie sesi web ATAU Bearer aud=bmad-mcp; kredensial lain 401.
- (constraint) Kontrak klien Go immutable: form-urlencoded, client_id literal bmad-mcp-cli, redirect_uri wajib http://127.0.0.1:<port>/callback (loopback, port dinamis), respons wajib memuat user.isAllowed, penolakan callback berbentuk error=access_denied; klien tidak mengirim scope.
- (constraint) Token MCP: JWT HS256 AUTH_SECRET issuer onyx-auth dengan aud=bmad-mcp; verifikator Bearer wajib menolak token tanpa aud tersebut (termasuk token akses web 15 menit).
- (constraint) Dual-auth REST BMad wajib karena agent-board-view.tsx konsumer cookie; jalur verifikasi cookie dan Bearer terpisah.
- (constraint) Penyimpanan OAuth (oauth_codes + refresh MCP) di blok schema v6 db.ts, append-only idempotent mengikuti pola v3/v4/v5; code dikonsumsi atomik (UPDATE ... WHERE consumed_at IS NULL RETURNING).
- (constraint) Gerbang isAllowed = users.status='Active'; tanpa migrasi kolom; pesan penolakan mengarah menghubungi admin tim.
- (constraint) POST /api/oauth/token publik tanpa sesi; halaman /oauth/authorize mengelola sendiri redirect ke /login (proxy tidak berubah).
- (constraint) expires_in respons = 2592000 detik sesuai contoh kontrak WEB_SPEC.
- (assumption) expires_in 2592000 (30 hari) diikuti meski JWT access tak dapat dicabut sebelum exp — klien membaca expires_in dinamis sehingga TTL dapat diperingkas kapan pun tanpa merusak klien.
- (assumption) AUTH_SECRET dan issuer onyx-auth yang sama dipakai untuk token MCP; klaim aud=bmad-mcp satu-satunya pembeda dari token web.
- (question) TTL refresh_token MCP belum ditetapkan sumber mana pun — usulan 30 hari (paritas access token) menunggu konfirmasi user.
- (question) Apakah REST BMad perlu memfilter data per team/role pemegang token, atau identitas user cukup (perilaku saat ini: tanpa filter)?
