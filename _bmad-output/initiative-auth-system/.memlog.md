- (requirement) R1 (design §1 §2): every nav page + admin surface gated by a permission key from one code catalog; new page = one catalog entry, no DB migration
- (requirement) R2 (design §3): roles are manageable data (create/rename/describe/duplicate/delete) with grants stored per role; 3 system roles seeded idempotently on boot
- (requirement) R3 (design §5): effective permissions derive from the user's role at request time; a grant/revoke takes effect at the API on the next request, no re-login
- (requirement) R4 (design §5): every data API route enforces its permission server-side (401/403); client-side hiding is never the only barrier
- (requirement) R5 (design §6): sidebar, command palette and deep links respect grants; no permission = menu hidden and page shows 403 view, never data
- (requirement) R6 (design §6): admin manages roles on /roles (master CRUD) and grants on /permissions (matrix), cross-linked via URL params
- (requirement) R7 (design §5): lockout structurally prevented (no own-role grant edit, no delete of role in use, no stripping last roles.manage) and every mutation audited (actor, action, diff)
- (requirement) R8 (design §2): wildcards (* and resource.*) supported, resolved to concrete catalog keys; unknown/dead grants are inert
- (requirement) R9 (design §9): resolver unit tests, per-role API fixture matrix (401/403/409), e2e per role — test runner added as prerequisite
